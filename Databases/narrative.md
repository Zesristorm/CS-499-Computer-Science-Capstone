# Database Narrative

For this enhancement, I selected my event tracking app from CS: Mobile Architecture and Programming. I originally created the app using Java, Android studio, and SQLite. The app lets users create an account, log in, add events, edit events, view a weekly schedule, or calendar, mark events complete, delete events, and use SMS reminders. I chose this app for my ePortfolio because it shows how much my database skills have improved. The original app worked, but the database had several problems. Passwords were stored as regular text, events were connected to usernames, and dates and times were stored separately. The old database update method could also delete saved accounts and events. 

One of the biggest improvements was password security. The app now stores a password hash and salt instead of the real password. I also added email addresses to user accounts. The old password reset only required username, which was not safe. The new process creates a six digit recovery code that expires after 15 minutes and the code can only be used once. The app does not send a real recovery email yet. During testing, the code appears in Logcat. A real version would need a secure email service or server to send the code. Even though email delivery is not connected, the database still stores and checks the recovery code safely. 

I also changed how users and events are connected. Each user now has a user ID and each event is connected to that ID. This is safer and more reliable than using only a username. The app also checks the signed-in user before editing to deleting an event. Event dates and times are now saved together in one format. This helps SQLite sort the events correctly. I added database indexes to make common searches faster. The week screen can also load several days with one database query instead of searching the database every time the user selects a new day. 

The hardest part was changing the database without losing old information. I created test accounts and events before running the update. The app copied the old information into the new database structure and changed the old passwords into secure hashes. I also learned that a successful build does not mean everything will work correctly. The app built successfully, but some database errors only appeared when I ran it. One query had the sorting command in the wrong place and one version of the events table was missing a column. I used Logcat to find the problem and fix them.

This enhancement mainly connects to outcome #4 because I used SQLite, database migrations, foreign keys, indexes, and queries to improve the app. It also connects to outcome #5 because I improved password storage, account recovery, user data protection, and database backups. I also made progress towards outcome #2 by making the database code easier to read and understand. My outcome plan stayed mostly the same, but I completed more security work than I first expected. While working on the database, I learned that one change could affect login, account recovery, event ownership, and several other parts of the app.
